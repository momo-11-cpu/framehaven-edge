## 适用场景

本项目围绕 **1080p、约 4 Mbps、24/25/30 fps 的普通 SDR HTML5 视频**开发，优先面向 Windows 上的 Microsoft Edge，适合个人观看真人影视、网络视频、动画和番剧。哔哩哔哩 1080p 播放是本项目实际观察过的使用场景；它不是仅针对某个站点的专用播放器。

- 想改善中低码率视频的压缩方块、振铃、颗粒和色带。
- 想将 25 fps 视频提升到 50 fps，或在性能与刷新率足够时以 4× 目标生成到 100 fps。
- 想保留原有网站播放器的播放操作、音频、网页字幕和弹幕层，而不安装本机推理服务。
- 想在本机比较算法效果、调节强度、检查哪些处理实际完成。

码率不是决定算力的唯一因素：解码后尺寸、源帧率、补帧倍率、AI 放大后的输出尺寸和其他 GPU 工作都会影响负载。4 Mbps 是开发参考场景，不是准入阈值或保证条件。

## 主要能力

| 功能 | 实现与行为 |
|---|---|
| 四种运行模式 | 关闭、真人、动画、自定义；关闭时停用所有增强 |
| AI 补帧 | Framegen v7s；2× 生成一个中间帧，4× 生成三个不同时刻的中间帧并复用公共计算 |
| 动画策略 | 共用 v7s 模型，识别重复画面，减少对动画停格和重复帧的无效推理；不是另一套动画专用权重 |
| 压缩修复 | FFmpeg 算法的 GPU 适配：去块、去振铃、递归双边降噪 |
| 去色带 | libplacebo deband 的 GPU 适配 |
| 真人后处理 | AMD CAS 自适应锐化、FSRCNNX 2× AI 放大 |
| 动画后处理 | Anime4K Restore S 线条修复、Anime4K CNN 2× S 放大 |
| 交互 | 算法开关、自定义组合、锐化强度、左右对比、逐站授权自动运行 |
| 运行诊断 | 每项算法的 GPU 完成状态和累计帧次；实际补帧呈现、迟到、忙碌跳过、显示丢弃、队列与刷新速率 |
| 声画协调 | 视频显示与声音使用相同固定缓冲延迟；跳转、模式切换时清理旧任务 |

真人/动画预设默认启用完整组合。去块、去振铃、降噪和去色带可按需关闭；修改核心补帧、锐化或 AI 放大项会进入自定义。2× / 4× 可直接选择，不需要更换模型。

模型、代码和权重随包提供。视频帧直接导入页面内的 WebGPU，补帧与空间增强共用设备，避免旧架构跨扩展 iframe 的全帧 CPU 回读/上传；仍存在必要的 GPU 纹理复制。场景分类仅回读少量统计值。使用完整源尺寸做补帧：1080p 补齐到 1088 行后裁回，默认不缩成 480p 推理。

## 能力上限与已知边界

- **输入安全上限为 1080p 高度**；启用 2× AI 放大时，1920×1080 会输出 3840×2160。4K 输出不等于支持原生 4K 输入。
- 补帧提供 2× / 4× 目标，**不保证所有设备、所有视频持续满帧**。60 fps 输入选择 4× 意味着 240 fps 目标，负载和显示要求很高。
- 显示器和页面刷新速率决定最终可见帧数。60 Hz 屏幕无法完整呈现 100 个独立帧；应同时看“目标”与“实际呈现”。
- 仅针对 SDR；没有 HDR 色彩管理、HDR→SDR 映射或 HDR 增强承诺。
- 不处理检测到 EME/DRM 的受保护视频，不绕过站点或浏览器的帧读取限制。跨域、音频访问与私有播放器行为可能导致回退。
- 当前仅正常 1× 速度启用补帧。暂停时可保留空间增强，后台标签页暂停增强；原生画中画、视频元素自身全屏和带原生 controls 的视频保留原生播放。网站播放器容器全屏是否可增强取决于其 DOM 结构。
- 处理会增加固定音视频缓冲，当前最低约 **200 ms**，不是面向游戏或实时通话的低延迟方案。原生 PiP 不能显示增强覆盖画布。
- AI 插值可能在遮挡、细线、字幕、强闪光、快速运动处产生伪影。修复与放大无法还原源视频不存在的真实细节，过度锐化也可能降低观感。
- 完成帧次只说明对应处理已完成，不等于每张图像都被屏幕显示。重复帧主动跳过、忙碌跳过、推理迟到和显示丢弃含义不同。
- 目前只有一套主要实测硬件；多显卡笔记本、其他驱动、系统与网站仍需要社区补充验证。

## 性能需求与测试设备

用户无需 Python、CUDA、WebNN、本机辅助程序或额外视频播放器。需要浏览器硬件加速、WebGPU，以及补帧所需的 `shader-f16` 支持。推荐先从 1080p、24–30 fps、2× 开始，再依据诊断切换 4×。

**已实测参考设备，不是最低配置：**

| 项目 | 配置 |
|---|---|
| GPU | NVIDIA GeForce RTX 4060 Ti，8 GB 显存 |
| CPU | Intel Core i5-14600KF，14 核 / 20 线程 |
| 内存 | 32 GB |
| 系统 | Windows 11 专业版 23H2，build 22631 |
| 浏览器 | Microsoft Edge 156.0.4314.58 |
| 驱动 | NVIDIA 566.36 |
| 观测页面刷新 | 约 165 Hz；属于测得的页面回调速率 |

项目发起者在上述设备完成日常使用测试，并反馈当前功能正常。此前一次 Edge 在线观察中，1080p 25 fps 的动态片段实际呈现约 49.7–50.7 fps；当时处于动画模式，重复画面会减少生成数量，观察期间模型迟到为 0，解码丢帧没有增加。一次整卡占用快照约 21%，**不能当作长期平均值或插件独占占用率**。

下面是同机独立 Dawn/D3D12 的**合成全增强处理测试**：1080p 输入，保留全部增强，输出 4K，按一个源帧间隔处理一次。它不包含真实视频解码、帧导入、屏幕呈现和音频，测试时可能存在其他视频负载。

| 模式 | 补帧倍率 | 单帧对中位耗时 | P95 |
|---|---:|---:|---:|
| 真人 | 2× | 16.40 ms | 36.10 ms |
| 真人 | 4× | 30.38 ms | 50.98 ms |
| 动画 | 2× | 13.90 ms | 14.83 ms |
| 动画 | 4× | 24.33 ms | 25.49 ms |

这里的毫秒数不是实际输出帧率，也不是所有内容的画质评分。有关测量口径、长尾、原始摘要和报告方法，见 [性能说明](docs/PERFORMANCE.md)。

## 其他显卡与 CPU 的兼容情况

| 平台 / 设备 | 当前结论 |
|---|---|
| RTX 4060 Ti + i5-14600KF + Windows Edge | 本项目实测参考组合 |
| 其他 NVIDIA GPU | 未逐型号实测；必须实际检测 WebGPU / shader-f16，不能只凭“RTX”名称保证性能 |
| AMD Radeon / Intel Arc / 核显 | 使用标准 WebGPU，没有代码层面的 NVIDIA 专用要求；未在本项目逐型号实测，不承诺与参考设备同等速度或画质稳定性 |
| AMD Ryzen / 其他 Intel CPU | 没有当前推理路径的 Intel 专用 CPU 指令要求；主要模型在 GPU 上运行，CPU 仍影响解码、网页调度和帧提交，尚无跨 CPU 基准 |
| 笔记本双显卡 / 低功耗设备 | 以浏览器实际选中的适配器为准；省电策略、共享内存和散热可能影响吞吐，建议 2× 起步 |
| Chrome | Chromium 技术路径适用，优先维护和实际验收平台仍为 Edge，未声明同等覆盖 |
| macOS / Linux | 无本项目独立验收；需要浏览器与驱动实际支持相关 WebGPU 功能 |
| Firefox / Safari / 手机浏览器 | 当前发布包不作为支持目标 |
| 无 WebGPU 或无 shader-f16 | 不支持当前完整 AI 补帧路径；不可把纯 CPU 当作等价实时回退 |

`minimum_chrome_version=121` 只是扩展声明的接口基线，不是所有 Chrome/Edge 121 设备都兼容的保证。完整说明见 [兼容矩阵](docs/COMPATIBILITY.md)。

## 安装与更新

1. 从 [GitHub Releases](https://github.com/momo-11-cpu/framehaven-edge/releases) 下载 `framehaven-edge-1.0.0.zip`，并可对照同名 `.sha256` 校验。
2. 解压到固定目录。在 Edge 打开 `edge://extensions`，开启“开发人员模式”。
3. 点击“加载解压缩的扩展”，选择直接包含 `manifest.json` 的目录。
4. 打开视频网页并播放，点击扩展，选择真人或动画模式，再点击“应用到当前页面”。可选择只允许当前站点自动运行。
5. 在补帧项选择 2× / 4×，查看每项状态及实际呈现。首次初始化会编译与测量 GPU 内核，准备期间继续原生播放。

更新时可以覆盖原来的固定目录，再在扩展管理页点“重新加载”，并刷新视频网页。不要同时启用两个版本。ZIP 是解压加载分发包；本项目尚未上架 Edge Add-ons，也不提供绕过浏览器签名规则的一键安装 CRX。

“更多设置 → 1080p 加速测试”可在浏览器内测试两种模式的 2× / 4× 完整合成管线并保存 JSON。测试与实际视频验收是两个步骤。

## 排查与常见问题

**已启用，但没有补帧？** 检查是否暂停、倍速、后台、原生 PiP、视频本身带 controls、受保护内容或浏览器无法访问帧。确认页面刷新后版本已更新，查看具体异常和逐项状态。

**GPU 不高，却没有达到目标？** 检查“忙碌跳过”“迟到”“显示丢弃”和页面刷新速率。浏览器线程调度、解码回调与显示时钟也可能形成瓶颈；整卡占用不能单独诊断。

**动画模式少补一些帧？** 重复画面、动画停格与镜头切换会主动保留源帧，减少无效插值；真人视频也可能包含重复帧。若想对照，可切换真人模式。

**为什么原帧修复与锐化的完成次数不同？** 原帧先做修复；原帧和生成帧都需要后续锐化/放大，因此后两项累计次数通常更多。

**关闭后声音是否恢复？** 恢复直接音频连接。Web Audio 的媒体元素绑定由浏览器保持；这不等于上传或录制了音频。

## 构建与参与贡献

```sh
# Node.js 24，pnpm 11
pnpm install --frozen-lockfile
pnpm check
pnpm package
pnpm release:verify
```

构建结果位于 `dist/`，安装包位于 `artifacts/`。当前模型和许可证随源码提供，构建前校验其 SHA-256。安装后的播放不需要开发环境。

核心目录：`src/engine/` 视频/GPU/补帧调度，`src/core/` 配置与状态，`src/ui/` 扩展面板，`vendor/` 上游源码及许可，`models/export/framegen/` 固定权重，`tests/` 回归测试。CI 验证类型、测试、构建、打包和资产完整性；普通云端 CI 不测真实 GPU 或网站画质。

反馈请附版本、系统、浏览器、GPU/驱动、CPU、输入尺寸/帧率、倍率及简短复现步骤。诊断可能含站点信息，公开前自行检查。欢迎按 [贡献指引](CONTRIBUTING.md) 补充其他硬件测试。
